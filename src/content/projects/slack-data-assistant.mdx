## The problem

Once the company had one operating platform, people started asking questions it had no page for: sales at one site this year versus last, the best sellers on a campus, why a machine went quiet. Those questions came to me from the CEO, hardware, marketing, partnerships and the field technicians. Each took 15–20 minutes to answer, but when I was busy, people waited hours.

Each answer was a fresh SQL query, and the same word could quietly mean two numbers. Does "sales" include refunds? Is a day in LA time or UTC? Two honest queries could disagree.

## What I built

A Slack agent anyone can ask in plain English. Before it writes any SQL, it looks up the business terms in the question in a written glossary: what a sale is (paid orders only, refunds and internal discounts left out), what in-stock % means, what counts as an active machine, and which time zone a date is in. It writes the query from those definitions and runs it on a separate copy of the data in a warehouse, never on the live system.

The first version answered from order data alone. The current one also reads machine uptime, a searchable archive of Slack messages and a log of site events, so it can explain a number, not just report it. Every figure is tagged with where it came from, guesses are labelled as guesses, and when the data cannot answer a question, it says so instead of approximating.

This is the same idea as an ontology or semantic layer: a shared map from the words people use to the data and formulas behind them, so every answer computes a metric the same way.

## Answers that changed decisions

When we rebuilt the menus for our university campuses, the top-seller answers came from the agent, with duplicate product names merged so the ranking was right. Those products are now top-3 sellers at 6 locations.

## An answer that changed the question

A hospital site showed eleven straight days of zero sales, which looked like demand falling off. The agent pulled uptime and order history and showed something else: the machine had been locked, then swapped for a new one, and weekly sales had been climbing right up to the day it stopped. It also caught that the new machine sells under a new location ID, so every later query for that site has to include both.

## Why the source is in every answer

People trust a number they can check. With the source and SQL attached, whoever asked, or anyone else in the thread, can see exactly what was counted before the number goes to a site partner or into a deck.
